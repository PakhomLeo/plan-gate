# Agent 规则

本文件由我维护，不得自行增删改。其他指示与本文件冲突时，以本文件为准。

## 处女原则

最高准则。和其他写法冲突时，先守这四条。探索期可以把一整块扔掉，但不能先打补丁再扔。扔掉就连根拔掉。

- 不打补丁。错了改产生错误的那一处，不在旁边加分支、包装、兼容层、开关或「先这样用」的特例。同一件事只留一种写法。第二次碰到同一处歪了，先改结构，不准再叠一层。
- 代码自解释。名字和结构自己说出做什么。读代码能懂的事不写注释。注释只写下次会猜错的事：为什么这样设计，谁调用，保证什么、不保证什么。需要大段说明才能看懂的代码，先改代码。
- 不留残渣。这次不用的函数、文件、参数、开关、注释掉的旧实现、过期 harness、当次说明，收工时清掉。临时方案到期就删，不准改名留下。
- 部署一致。本地走通的路径就是交付的路径。不为某一台机器、某一个环境写特例。不用假数据或假 mock 换绿灯。构建过、数据流程过，换到交付侧必须还是同一套。

这是探索阶段的 demo，不是上线服务。当前功能和组件都可能被整个扔掉。骨架按上线标准留边界，现在不加安全检查、权限、重试、缓存。为临时组件铺这些，使项目变臃肿，不可接受。

四份文档：本文件是文档1，`docs/MAP.md` 是文档2，`docs/HARNESS.md` 是文档3，`docs/TASK.md` 是文档4。文档2和文档4都是功能决策。文档2抽象，但选择必须写准，并写清项目框架、用户操作流程、数据流程。文档4只负责当前这一次，开工前先写完再写代码，细到函数和要改的其他组件。

编写前按文档1、文档2、文档3读。代码实施阶段文档1和文档4优先，文档2和文档3次之。文档4管这一次为什么做、怎么做、碰到哪里。文档2管已经定下的功能选择和两条流程。文档3管已经固定下来的 harness，实施时不要对着它改代码。Harness 写什么、什么算、怎么跑，只看文档3。

新开会话只读本文件、`docs/MAP.md`、`docs/HARNESS.md`。代码细节不进这三份。`harness/` 里的实现不进平常上下文，只有要改某一条 harness 时才读那一条。小的单条决策写在代码注释里，不进文档2，也不进文档3。

开工前按简化技术语言（ASD-STE100 规格）写文档4——短句、常用词、一个词一个意思、主动语态：这次为什么做；怎么做，细到函数和代码路径；会碰到哪些其他组件，哪些情景下怎么表现；哪些不要顺手做。对照本文件和文档2，写明改哪里、为什么。和文档2有冲突就写出要改的那一句。我明确说可以施工之前，不得改代码，不得改文档2，不得改文档3。

跟我说话（描述、提问、回复）都用简化技术语言：短句、常用词、一个词一个意思；少用函数名、字段名，必须提时先用一句大白话说明。

代码要短，路径要直。高内聚：一个模块只因一件事变化。低耦合：只依赖对方一个窄而稳定的面，不依赖它的内部结构、调用顺序或私有字段。层数不设上下限。每多一层，必须说得出它今天隔开的是哪两个已经存在的东西。说不出第二个真实用途，不得新起一层、框架、扩展点或开关。要合并已有的层，先停下来问。

入口负责进出，里面负责规则。外部数据只在入口看一次。失败直接返回，不得包成看起来成功的空结果。会变的值集中放。新行为另起一处，不在旧处加开关兼容两边。同一件事只写一处。能沿现有结构完成，就不得新起结构。现有结构已经歪了，改那一处，不打补丁。

## Harness

Harness 是已经写好的代码对照文档2反推出来的回路，用来防止后面的修改把已经确定的核心弄失效。详细的编写要求、什么算什么不算、怎么使用、现有条目，只看文档3。

文档3开工时不写条目。一大块做完、对照文档3评估过确实该留，才申请。我点头才写入文档3，并在 `harness/` 写实现。不同意就丢掉，不追问第二次。过期条目同样申请后才删，不留残渣。

一次大任务只有收工、准备交付 git 之前这一次运行机会。不许边写边测。先按文档4的验收边界看这一次，再跑文档3已登记的 harness。跑不通才改代码，改完再跑这一次。不得把已登记项放宽来换绿灯。

设计文档和 harness 登记都会随项目变。收工时检查有没有要加的，列出改前句和改后句，我点头才写入。一次性 bug 和偶发问题不进设计文档，也不进 harness。
