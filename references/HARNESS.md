# Harness 文档

这是文档3。平常只读这一份，不读 `harness/` 里的实现。要改某一条，才把那一条的实现加进上下文。

Harness 是回路，不是考题：检查，验证结果，阻断错误，把失败反馈回来。它从已经写好的代码对照文档2反推，用来防止后面的修改把已经确定的内容改错。不是开工前写完的规格。晴天走通只说明这次能开。Harness 要在暴雨里还开得动。

## 1. 编写要求

一条 harness 必须同时说清这七件：

- 测什么：哪一条已经确定的流程或规则
- 目标：保住文档2里的哪一个选择
- 为什么需要：后面一次修改怎样会把这里弄失效，失效后为什么表面还能跑
- 场景：从哪开始，数据或操作是什么
- 操作：实际走哪条路径
- 必须得到什么
- 不能出现什么

缺一件就不算一条。硬字段检查可以写进「必须得到」或「不能出现」，但不能单独成一条。主形态是真实数据或真实操作流程。不用假 mock。失败必须挡住交付，并返回哪一条、坏在场景、操作、结果、禁止结果的哪一段。不得改成看起来成功的空结果。

入口写在下面每一条上。实现放 `harness/`，文件名和这里的条目同名。平常编写代码不读这些实现。

## 2. 什么算，什么不算

算：整块核心流程；改错会导致功能崩塌的地方；反复出错、已经确认还会再碰到的业务逻辑。三者都必须已经写在代码里。

不算：小的单条决策；一次性界面调整；还在探索、经常改口的功能；开工前凭想象写的考题；为覆盖率加的空值、权限、并发、重试；假 mock 换来的绿灯。

一大块做完、评估后才申请。我点头才加入本文件，并编写实现。不同意就丢掉，不追问第二次。模块改了、这条不再保住任何约定：申请改本文件，并删掉过期实现。

## 3. 怎么使用

收工、准备交付 git 之前才跑。施工中途不跑。

先按文档4的验收边界看这一次，再跑下面已登记的全部条目。跑不通改代码，不得放宽条目，不得删条目来换绿灯。改完再跑这一次。

跑法：进入仓库，执行该条写明的入口。入口要能独立跑完这条真实流程。不要把 `harness/` 加进编写代码时的上下文。
